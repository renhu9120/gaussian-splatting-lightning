# 实验输出目录结构说明

## 一、设计目标

- **按方法区分**：baseline、Phase A、以及后续新方法（Phase B 等）各自独立，不与数据集或 step 混淆。
- **一次实验一个根目录**：以「方法 + 数据集名称」为文件夹名，便于复现、对比和写论文。
- **目录内分层**：同一实验的「训练原始结果」「验证结果」「汇总图表」放在同一根目录下不同子目录中，结构清晰。

---

## 二、推荐结构（经典模式）

常见做法有两种：

1. **按实验聚合（Experiment-Centric）**  
   每个实验一个根目录，下面再分 train / validate / figures。  
   适合：同一方法同一数据集只跑一次（或少数几次），结果要长期保留、写论文用。  
   本方案采用此种。

2. **按 run 聚合（Run-Centric，如 MLflow）**  
   每个「运行」一个带时间戳或 ID 的目录，里面再按 artifact 类型分子目录。  
   适合：同一配置反复跑、需要对比多次 run 的场景。

本仓库采用 **Experiment-Centric**：  
根目录名 = **方法_数据集**（如 `baseline_lego`、`phase_a_lego`），下面固定子目录含义一致。

---

## 三、统一目录布局

```
outputs/
├── baseline_lego/                    # 方法_数据集（一次实验一个根目录）
│   ├── checkpoints/                  # 训练产生的 checkpoint
│   │   ├── epoch=0-step=101.ckpt
│   │   ├── ...
│   │   └── epoch=0-step=10000.ckpt
│   ├── version_0/                   # 或 lightning_logs/version_0/（训练时 config/日志）
│   │   └── config.yaml
│   ├── config.yaml                  # 若 CLI 直接写在根目录
│   ├── validate/                   # 该实验的验证结果（按 step 分子目录）
│   │   ├── step00101/
│   │   │   ├── metrics/
│   │   │   │   └── xxx-step=101.csv
│   │   │   └── val/
│   │   │       └── epoch=0-step=101/
│   │   │           └── *.jpg
│   │   ├── step00501/
│   │   ├── step01001/
│   │   ├── step03001/
│   │   ├── step05001/
│   │   └── step10000/
│   └── figures/                     # 汇总与论文用（make_training_progress_figure 等）
│       ├── metrics_summary.csv
│       ├── metric_curves.png
│       └── iterative_progress_xxx.png
│
├── phase_a_lego/                    # 另一方法 + 同一数据集
│   ├── checkpoints/
│   ├── validate/
│   │   ├── step00101/
│   │   └── ...
│   └── figures/
│
├── baseline_chair/
├── phase_a_chair/
└── ...
```

**要点**：

- **根目录**：`outputs/<方法>_<数据集>/`，例如 `baseline_lego`、`phase_a_lego`。
- **训练原始结果**：checkpoints、config、lightning 日志等均在根目录或 `version_0/` 下，与现有 Lightning 行为一致。
- **验证结果**：统一放在该实验下的 `validate/stepXXXXX/`，每个 step 一个子目录，内含 `metrics/` 与 `val/`（渲染图）。
- **汇总与论文**：`figures/` 下存放 `make_training_progress_figure.py` 生成的 CSV、曲线图、迭代进度图等，便于论文撰写和结果汇总。

---

## 四、与常见范式的对应

| 概念         | 本方案                     | 说明 |
|--------------|----------------------------|------|
| 实验标识     | `方法_数据集`              | 如 baseline_lego、phase_a_lego，一目了然。 |
| 训练产物     | 根目录下 checkpoints/ 等   | 与 Lightning 默认输出一致，便于找 ckpt。 |
| 验证产物     | `validate/stepXXXXX/`      | 按 step 分目录，避免与训练文件混在一起。 |
| 论文/汇总    | `figures/`                 | 与原始数据分离，便于版本管理和投稿。 |

---

## 五、向后兼容与迁移

- 若 case 未设置 `output_dir`，则 `experiment_output_dir` 返回 `train_exp_name`，行为与之前一致。
- 当前 baseline 与 Phase A 的 case 已统一设置 `output_dir`（如 `baseline_lego`、`phase_a_lego`），新跑的实验会进入上述结构。
- **若你已有旧目录**（如 `outputs/lego_quaternion_phase_a/`）：  
  - 可将该目录重命名为 `outputs/phase_a_lego/` 以接入新结构；  
  - 或暂时去掉该 case 的 `output_dir`，继续用原路径验证，再择机迁移。

---

## 六、make_training_progress_figure 的用法

- **输入**：指定一个实验根目录（如 `outputs/phase_a_lego`）。
- **逻辑**：在该目录下的 `validate/` 中查找 `step00101`、`step00501` 等子目录，读取各 step 的 `metrics/*.csv` 与渲染图。
- **输出**：在同一实验根目录下的 `figures/` 中写入汇总 CSV、曲线图、迭代进度图等。

这样每个「方法_数据集」实验都自带一份 figures，便于与 baseline 对比和写论文。
